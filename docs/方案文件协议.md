# 目录方案文件 v1

方案生成与文件执行相互独立。内置分组、外部程序或 AI Agent 都可以生成 `tidy-plan`；Tidy 统一负责检查、预览、应用及目录恢复。本协议不要求特定 AI 平台或 API Key。

## 流程

1. 在整理工作区选择「方案文件 → 导出素材清单」，获得 `tidy-catalog`。它包含素材 ID、可信时间、GPS、设备、来源目录、文件的相对路径和 SHA-256。一组伴生媒体共享一个素材 ID。
2. 同时导出当前方案作为完整模板。修改 `groups` 的目录和 ID 分配，保留 `catalogFingerprint`。不要推测 ID 或将同一项放进多个目录。
3. 导入方案文件。校验通过后只创建候选；选择「采用新方案」才替换草稿。导入不直接操作文件。
4. 从「查看变更」再次检查实际磁盘，确认后应用。

清单包含私有照片元数据；是否将其交给外部服务由用户自行选择。导入文件中的根目录、任意源路径或命令不构成执行授权，执行范围始终来自当前工作区及本地索引。

## 结构

下面的 ID 与指纹为占位符，需要替换为导出清单中的原值。实际方案必须覆盖清单中的每一项。

```json
{
  "format": "tidy-plan",
  "version": 1,
  "catalogFingerprint": "从导出文件原样保留",
  "groups": [
    {
      "folder": "事件/2025/2025-10-01—10-10 旅行/10-01",
      "eventRoot": "事件/2025/2025-10-01—10-10 旅行",
      "kind": "trip",
      "reason": "同一次多日行程",
      "review": true,
      "fixed": true,
      "ids": ["素材ID一", "素材ID二"]
    },
    {
      "folder": "待确认/日期缺失/手机备份",
      "kind": "unresolved",
      "review": true,
      "fixed": false,
      "ids": ["素材ID三"]
    }
  ]
}
```

- `catalogFingerprint` 绑定素材身份、文件内容哈希及来源路径。源清单变化后必须重新导出。
- `folder` 是相对目录，禁止绝对路径、上级目录、Windows 保留名称和非法字符。
- `ids` 必须精确覆盖所有素材，各出现一次。遗漏、重复分配或未知 ID 会被拒绝。
- `eventRoot` 可选，是多日行程或事件的父目录，必须包含 `folder`。
- `kind` 可选：`existing`、`event`、`trip`、`daily`、`life`、`theme`、`reference`、`unresolved`。仅用于分类展示，不决定执行权限。
- `reason` 可选，最多 300 字符，应写可核对的分组依据。
- `review` 默认为 `true`，表示需要检查。
- `fixed` 默认为 `true`，重算时保留该归属；设为 `false` 表示允许内置算法重新判断。
- 可选 `rules` 使用整理规则的完整结构；不提供则沿用当前规则。
- 多个组可以指向同一目录以保留不同审核状态，但不能产生同名目标文件。存在同名来源时，应保留来源子目录，不可丢弃其中一项来通过验证。

导入不会修改 `files`、哈希或照片元数据，也不会执行 JSON 中出现的脚本、URL 或任意命令。单个方案文件最大 8 MB。

## API

以下接口均在 `/api/organization` 下：

| 接口 | 行为 |
|---|---|
| `GET /export/catalog?root=...` | 导出当前素材清单 |
| `GET /export/plan?root=...` | 导出当前完整方案 |
| `POST /import`，正文 `{root, revision, plan}` | 校验并创建候选，返回 `candidateId` 与候选草稿 |
| `POST /accept`，正文 `{root, candidateId}` | 以修订号检查并采用候选 |

后续应用必须另经 `/preview` 和 `/runs/:id/apply`。外部 Agent 不需要直接操作真实文件。
