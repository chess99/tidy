# 目录整理与历史版本

「整理」是独立工作区。先基于已扫描文件生成目录草稿，在草稿中审核和调整，再通过「查看变更 → 应用到磁盘」在所选扫描根内移动文件。它以物理文件实例为单位，同内容的两份文件不会合并。

## 使用

1. 选择已启用的扫描根，生成方案。目录树用于定位，文件夹卡片用于浏览分组；进入末级目录后查看照片网格。RAW 与同目录同主名的成片作为一个调整单位。
2. 勾选照片或文件夹，在「目标目录」输入已有或新的相对路径。选取一部分可拆分，选取多个组可合并；「调整此目录」选中整个目录以修改归属。调整会自动保存，当前会话支持最近 30 次手动调整的撤销、重做。
3. 「确认当前分组」固定归属并移出待检查列表。「允许重新分组」解除固定，下次生成时重新判断。
4. 在规则面板改变事件间隔、最长跨度、最小数量、日常归拢周期或独立主题。重算先展示归属差异，采用后替换草稿；未采用不改变现有草稿。人工固定项始终保留。
5. 查看变更。后台检查当前目录、计算缺少的 SHA-256、发现伴生文件并检测目标冲突。同主名的 XMP、AAE、DOP、PP3、SRT、LRF、THM 会随媒体移动。确认后才执行移动。大目录首次校验可能较慢，状态在弹窗中更新，关闭弹窗不取消执行。
6. 在「历史记录」浏览已记录的目录，或预览恢复计划。恢复也走同样的检查和执行流程。
7. 「方案文件」可导出素材清单、导出当前方案或导入外部方案。导入先验证清单身份及分配完整性，再显示差异；只有采用才改变草稿。参见 [方案文件协议](方案文件协议.md)。

## 推荐规则的实际能力

- 拍摄片段：按可信时间和位置形成连续片段。默认停拍间隔 8 小时；夜间可容忍 18 小时；同设备缺定位的短暂停拍可适度连接。局部事件最多跨 2 天，常住区域的不同拍摄日不会仅因时间接近而合并。
- 多日行程：参考前后 90 天的定位，使用至少 8 个拍摄日且跨 30 天的区域作为常住候选。离开常住区域后，可连接跨夜及不超过 72 小时的停拍，最多 21 天；返回常住区域结束行程。无常住证据时，短期连续多日定位仅提出「多日记录」候选。行程保留一个父目录，按日创建子目录。
- 日常：长期反复出现的生活区域中的零散记录，标为待检查。不会仅凭旅行连续拍了 5 天就判为日常，也不推断「工作」「散步」等活动意图。
- 主题：显式配置主题，优先使用现有标签和目录名称；AI 服务可用且已有当前模型向量时，使用文本相似度补充候选。分数是模型证据而非概率，匹配结果需要审核；缺向量或服务失败有明确提示。
- 生活散片：其余带日期的照片按区域和年/月归拢。未命名区域以粗粒度坐标显示，可在单张预览中为附近 5 km 区域命名。
- 截图和应用导出按名称/来源分流到「资料」；日期缺失进入待确认。已有日期命名目录默认沿用。

本版的分组是启发式建议，并非对旅行、人物关系或生活阶段的语义定论。地点使用现有 GPS 与手动区域名称，不调用在线地理编码。主题为空时不运行语义匹配。

## 版本语义

快照记录相对路径、文件实例 ID、SHA-256、大小、修改时间和空目录；不保存照片字节。快照范围是所选根内的普通文件，排除 Tidy 数据目录和已配置回收站。未入库的普通文件也会被记录，但不参与推荐分类。

- 草稿编辑与规则候选不产生正式整理记录。
- 应用前，若当前状态不同于最近记录，自动记录「应用前状态」。完全相同的目录状态复用快照，整理记录仍按执行时间追加。
- 所有移动核验成功后记录新状态；应用成功保留草稿的人工归属并更新来源路径。
- 恢复时保留后来新增的文件；缺失、内容变化或无法唯一识别的文件显示为跳过。目标被占用则阻止执行，不覆盖。恢复完成追加记录并清除过期草稿。
- 已删除或覆盖的内容不能凭目录快照恢复。目录版本不替代备份，也不恢复 Immich 等外部图库的相册、人脸或资产关系。

## 执行与恢复

准备/应用期间暂停 Tidy 后台队列，并阻止其他修改接口；开始前要求正在运行的后台任务完成。检测到磁盘状态或草稿修订号变化时，旧计划失效，必须重新检查。预检支持取消，显示当前文件及文件总数；使用最多 4 个并发读取降低 NAS 往返开销。实际执行可以暂停，会在当前文件操作完成后停止，之后可继续或恢复应用前目录。

移动前逐文件核对实际 SHA-256。同一次运行内，同卷移动的文件若实例身份、大小及修改时间不变，可复用已核实的内容证明；重启或身份变化后重新校验。先将源文件暂存至所选根下专属 `.tidy-stage-<runId>` 目录，再写入目标位置，支持路径互换。目标通过排他创建获得；同卷使用临时硬链接后移除源路径，不留下额外副本，不支持时使用排他复制并校验。符号链接、目录穿越和重名冲突会阻断。

执行计划及每个文件的检查点持久化。中断或失败后可继续执行，也可选择「恢复应用前目录」撤回已完成的部分移动；两条方向都会再次核对已暂存/交付文件。撤回同样支持中断后继续，保留后来新增的文件，遇到原路径被占用则阻断。内容发生变化时保留现场并报告具体文件，不将部分执行标记为完成。未开始移动的中断检查可以放弃。仅空目录发生变化的历史版本也可以恢复。

检查会记录解析后的真实根路径，执行和恢复前核对挂载目标，避免同一盘符切换到其他存储后重放旧计划。

## 算法与人工辅助的评估

`server/scripts/evaluate-organization.js` 在已有草稿上做内存试算，关闭目录保护、清空人工约束和主题。它比较已命名事件的分散程度、主组保留比例及是否混入其他已命名事件；多日行程按父目录比较，日目录不算把行程拆散。生活阶段、日期缺失和年份异常不宜当作严格的事件标准。

示例：`node server/scripts/evaluate-organization.js --baseline 1f78dd4 --output data/organization-evaluation.json`。命令只读取当前草稿，并可从 Git 读取旧版本用于对照；不会改变草稿和磁盘。指标仅反映这批参考目录，不是模型的一般准确率。

`server/scripts/compose-organization-plan.js` 可将明确的审核决策与自动分组组合：引用已有事件目录、按时间及设备补入候选、给已审阅的组命名，或使用本地同模型参考图向量提出主题。已有人工固定项优先；同名文件保留来源子目录，不做去重。结果是普通方案文件，仍经同一个导入验证和落盘预览。个人决策及含照片路径的报告应放在忽略跟踪的 `data/` 下，不进入代码仓库。

## 实现入口

- `server/src/services/organization/model.js`：素材合组与规则/名称验证；`clustering.js`：时间片段、区域证据和多日行程。
- `plan.js`：素材清单与方案导入导出协议。
- `filesystem.js`：目录检查、内容指纹、恢复匹配与移动计划。
- `service.js`：草稿、候选、应用、恢复与执行检查点。
- `store.js`：启动时幂等创建 `organization_drafts`、`organization_candidates`、`directory_snapshots`、`directory_history`、`organization_runs`、`organization_moves`。升级无需手动 SQL。
- `/api/organization`：范围/草稿/历史；`generate` 与 `accept` 分开；`preview` 创建后台检查；`runs/:id` 查询，`runs/:id/apply` 应用或继续执行，`runs/:id/rollback` 撤回未完成的移动；`snapshots/:id` 浏览历史内容；`export/plan`、`export/catalog` 与 `import` 提供方案文件通路。
- `client/src/components/organization`：目录工作区、历史浏览与审核交互。

持久化数据位于 Tidy SQLite 中，数据库也需要备份。执行日志只更新单个文件检查点，避免每次移动重写全库快照。

验证：`cd server && npm test -- --runInBand src/services/organization/__tests__`。
